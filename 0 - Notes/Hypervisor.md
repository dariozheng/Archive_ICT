Device virtualization lets one physical server present itself as many independent machines. The component that makes this possible is the hypervisor: a layer that abstracts CPU, memory, storage, and network interfaces away from the physical hardware and hands each guest its own virtual set. This note documents hypervisors with a networking emphasis — how a [[#Virtual Machine|virtual machine]] is given a network adapter, how the [[#Virtual Switch|virtual switch]] inside the host moves its frames, how VLANs are applied, and how that internal switching plane meets the physical enterprise network. It closes on the contrast between virtual machines and [[#Containers versus Virtual Machines|containers]].

## Hypervisor Classification

_A hypervisor — also called a virtual machine monitor (VMM) — creates and runs virtual machines; the two classes differ by where the hypervisor sits relative to the hardware._

Every hypervisor does the same core job: intercept the guest's privileged instructions and hardware access, and multiplex the real CPU, memory, disk, and NICs across many guests. What distinguishes the two classes is whether the hypervisor talks to hardware directly or goes through a conventional operating system to reach it.

### Type 1 — Bare-Metal Hypervisor

Installed directly on the physical hardware with no host operating system beneath it. The hypervisor owns the hardware and schedules the guests itself, which makes it thin, efficient, and strongly isolated — the standard for data-center and enterprise virtualization.

```
Type 1 — bare-metal
┌────────┬────────┬────────┐
│  VM    │  VM    │  VM    │   guest OS + apps
├────────┴────────┴────────┤
│        Hypervisor        │   runs on the metal
├──────────────────────────┤
│    Physical hardware     │
└──────────────────────────┘
```

Common examples used to illustrate the class are VMware ESXi, Microsoft Hyper-V, and KVM.

### Type 2 — Hosted Hypervisor

Runs as an ordinary application on top of a host operating system, and relies on that host OS to reach the hardware. The extra layer adds overhead and weakens isolation, but it is convenient on desktops and in labs where the machine is also used for other work.

```
Type 2 — hosted
┌────────┬────────┐
│  VM    │  VM    │   guest OS + apps
├────────┴────────┤
│   Hypervisor    │   an app on the host OS
├─────────────────┤
│    Host OS      │
├─────────────────┤
│    Hardware     │
└─────────────────┘
```

Common examples are VMware Workstation, Oracle VirtualBox, and VMware Fusion.

### Choosing Between the Two

|Property|[[#Type 1 — Bare-Metal Hypervisor\|Type 1]] (bare-metal)|[[#Type 2 — Hosted Hypervisor\|Type 2]] (hosted)|
|---|---|---|
|Sits on|Physical hardware|A host operating system|
|Overhead|Low — direct hardware access|Higher — guest access is relayed through the host OS|
|Isolation|Strong|Weaker (a host-OS compromise affects all guests)|
|Typical use|Servers, data centers, cloud|Desktops, development, testing|
|Examples|ESXi, Hyper-V, KVM|Workstation, VirtualBox, Fusion|

> [!note] KVM and Hyper-V blur the line Both are counted as Type 1 because the hypervisor executes in the kernel with direct hardware access. KVM is a Linux kernel module that turns the running kernel into a bare-metal hypervisor; Hyper-V, once its role is enabled, slides beneath Windows so that Windows itself becomes a privileged parent partition. The presence of a full OS alongside the hypervisor is why they are sometimes called hybrid, but their guest scheduling is bare-metal, not hosted.

## Virtual Machine

_A VM is a software computer: virtual CPU, memory, storage, and one or more [[#Virtual NIC|virtual network adapters]], each carved out of the host's physical resources by the hypervisor._

The hypervisor schedules each virtual CPU onto real CPU cores, backs virtual memory with host RAM, and presents virtual disks as files or block devices. From the guest's point of view it is running on ordinary hardware and is unaware of its neighbors. For networking, the piece that matters is the adapter the guest is given.

### Virtual NIC

_The VM's point of attachment to the network; from the guest's view it is an ordinary Ethernet card._

Each virtual NIC has its own MAC address — auto-generated by the hypervisor or set statically — a driver inside the guest, and a link to one port on the [[#Virtual Switch|virtual switch]]. The guest sends and receives Ethernet frames exactly as it would on physical hardware; the hypervisor moves those frames between the vNIC and its switch port in memory.

### Emulated versus Paravirtualized Adapters

_Two ways to present a NIC to the guest, trading compatibility against performance._

|Adapter model|How it works|Tradeoff|
|---|---|---|
|Emulated (e1000, e1000e)|The hypervisor imitates a real Intel NIC. The guest loads its normal driver and needs no awareness that it is virtual.|Maximum compatibility, but every frame is emulated in software — lower throughput, higher CPU.|
|Paravirtualized (VMXNET3, virtio-net, Hyper-V synthetic)|A virtualization-aware adapter. The guest loads a special driver and cooperates with the hypervisor through a shared memory channel.|Needs guest drivers (VMware Tools, virtio, or integration services), but delivers high throughput at low CPU cost.|

> [!tip] Use paravirtual in production Emulated adapters exist for compatibility during install or with old guests. For any workload that moves real traffic, the paravirtual adapter is the correct choice.

## Virtual Switch

_The software Layer-2 switch inside the hypervisor; it connects vNICs to one another and, through uplinks, to the physical network._

The virtual switch (vSwitch) is where hypervisor networking lives. It is a simplified Ethernet switch implemented in the host: virtual machines plug into its ports, physical NICs attach as [[#Uplinks and NIC Teaming|uplinks]], and it forwards frames by destination MAC address.

### Anatomy of a Virtual Switch

The vSwitch has two kinds of attachment points. Virtual ports face inward and connect to vNICs; uplink ports face outward and connect to the host's physical NICs (pNICs). Forwarding is plain Layer-2 lookup on the destination MAC.

```
        VM-A         VM-B         VM-C
         │ vNIC       │ vNIC       │ vNIC
      ┌──┴────────────┴────────────┴──┐
      │         Virtual Switch         │
      │      (Layer-2 forwarding)      │
      └────────┬──────────────┬────────┘
            uplink0        uplink1        ← physical NICs (pNICs)
               │              │
      ┌────────┴──────────────┴────────┐
      │        Physical Switch          │
      └─────────────────────────────────┘
```

### How Virtual Switching Differs from Physical Switching

_The vSwitch is deliberately simpler and safer than a physical switch — several behaviors you rely on in hardware are absent by design._

|Physical switch|Virtual switch|
|---|---|
|Runs spanning tree to break loops|Runs no STP and sends no BPDUs — it never forwards a frame from one uplink out another uplink, so it cannot create a loop|
|Learns source MACs from all traffic and floods unknown destinations|Knows its VMs' MACs authoritatively (registered when the vNIC connects) — it does not learn external MACs and does not flood to find them|
|Interconnects all ports, including trunk-to-trunk|Uplinks are exits to the physical world, not links the switch bridges to each other|
|Negotiates trunks (DTP), can route between VLANs|No dynamic negotiation, pure Layer-2, no routing|

Because it never bridges one uplink to another, the vSwitch removes the loop risk that spanning tree exists to solve — which is why it can safely attach several uplinks to the same physical fabric without STP.

> [!info] The exception — nested virtualization Newer vSwitch versions can enable an optional MAC-learning mode for edge cases such as running ESXi inside a VM (nested virtualization) or certain overlay designs. It is off by default; the behavior described above is the default and the one to describe for the exam.

### Traffic Paths Through the vSwitch

_Where a frame actually travels depends on where its destination lives — and only some paths ever reach the physical network._

#### Intra-Host — VM to VM on the Same Host

Both endpoints hang off the same vSwitch, so the frame is switched entirely in host memory. It never touches a physical NIC or the physical switch.

```
VM-A ─┐
      ├─► vSwitch (memory) ─► VM-B
VM-B ─┘
   no pNIC, no physical switch involved
```

This is fast, but the traffic is invisible to the physical network — external firewalls, ACLs, and monitoring never see it. Segmentation between same-host VMs must be enforced in the virtual layer.

#### Host to External Network

The destination is not a local VM, so the vSwitch forwards the frame out an uplink to the physical switch.

```
VM-A ─► vSwitch ─► uplink0 ─► Physical Switch ─► rest of network
```

#### VM to VM on Different Hosts

The frame leaves the source host's vSwitch through an uplink, crosses the physical network, and enters the destination host's vSwitch. Two virtual switches, joined by the physical fabric.

```
Host 1                         Host 2
VM-A ─► vSwitch ─► uplink ─┐
                           ▼
                    Physical Switch
                           │
                           └─► uplink ─► vSwitch ─► VM-B
```

### Uplinks and NIC Teaming

_One or more physical NICs bound to a vSwitch provide external connectivity, redundancy, and aggregate bandwidth._

An uplink is a physical NIC assigned to the vSwitch. Binding several pNICs to the same vSwitch is called NIC teaming: it survives the loss of a link or a physical switch, and it spreads load across the members.

#### Load-Balancing Policies

|Policy|How traffic is placed on uplinks|Physical-switch requirement|
|---|---|---|
|Originating virtual port ID|Each vNIC is pinned to one uplink based on its virtual port|None — the default, and the simplest|
|Source MAC hash|Uplink chosen by hashing the VM's source MAC|None|
|IP hash|Uplink chosen by hashing source and destination IP|Requires EtherChannel / LACP on the physical switch|
|Physical NIC load (LBT)|Rebalances VMs across uplinks by actual utilization|Distributed switch only|

#### Failover and Failback

Team members are marked active or standby. Link-state or beacon probing detects a failed uplink and moves its traffic to a surviving member. When an uplink fails over, the vSwitch can notify the physical switch by emitting frames from the moved MACs so the physical switch updates its MAC table to the new port. Failback returns traffic to the primary uplink once it recovers.

> [!important] Notify-switches keeps the CAM table correct Without the notification, the upstream switch would keep sending a VM's traffic toward the failed uplink until its MAC table aged out. The gratuitous frames make the cutover near-instant.

### Port Groups

_A named policy template on the vSwitch; vNICs join a port group and inherit its VLAN, teaming, and security settings._

Rather than configure each virtual port individually, ports are grouped. A port group carries a VLAN ID, a teaming and failover policy, traffic-shaping limits, and Layer-2 security options such as promiscuous mode, MAC-address changes, and forged transmits. A vNIC placed in a port group inherits all of it. Host-owned ports for management, live migration, and IP storage (VMkernel ports in VMware) are a special case of the same idea. Other hypervisors express the equivalent settings per adapter or per switch.

## VLAN Integration

_How the hypervisor participates in 802.1Q VLANs — three tagging models, distinguished by where the VLAN tag is applied._

A hypervisor host usually connects to the physical switch over an 802.1Q trunk so that many VLANs share one uplink. Which device writes and reads the VLAN tag defines the three modes below.

### External Switch Tagging (EST)

The [[#Port Groups|port group]] is set to VLAN 0, meaning no tagging in the vSwitch. All VLAN work is done by the physical switch, whose host-facing port is a plain access port. Each uplink effectively carries a single VLAN.

```
EST — physical switch tags
Guest (untagged) ─► vSwitch (untagged) ─► access port ─► switch applies VLAN
```

### Virtual Switch Tagging (VST)

The port group is set to a VLAN ID in the range 1–4094. The vSwitch adds the tag as frames leave toward the uplink and strips it on the way in, so the guest never sees a tag. The physical port is an 802.1Q trunk. This is the common, recommended model — many VLANs over one trunked uplink, transparent to the VMs.

```
VST — vSwitch tags
Guest (untagged) ─► vSwitch adds tag (e.g. VLAN 20) ─► trunk port ─► network
```

### Virtual Guest Tagging (VGT)

The port group is set to VLAN 4095, the all-VLANs wildcard. Tags pass through the vSwitch untouched, and the guest operating system applies and removes 802.1Q tags itself, so it can see and use multiple VLANs on one vNIC. Used when the VM is itself a router, firewall, or another virtual appliance that needs trunk visibility. The physical port is a trunk.

```
VGT — guest tags
Guest adds/removes tag ─► vSwitch passes tag through ─► trunk port ─► network
```

### Choosing a Tagging Mode

|Mode|Port-group VLAN|Who applies the tag|Physical port|Typical use|
|---|---|---|---|---|
|EST|0 (none)|Physical switch|Access|Single-VLAN hosts, simple setups|
|VST|1–4094|Virtual switch|802.1Q trunk|The default for multi-VLAN hosts|
|VGT|4095 (all)|Guest OS|802.1Q trunk|VMs that are routers, firewalls, or trunk-aware appliances|

## Standard versus Distributed Switches

_The same forwarding behavior, differing in where the switch is configured and managed._

### Standard Virtual Switch

Defined and configured on each host individually. It is simple and needs no extra licensing, but its configuration must be recreated identically on every host, so large clusters risk configuration drift. In VMware terms this is the vSphere Standard Switch (vSS).

### Distributed Virtual Switch

A single logical switch that spans many hosts. Its control plane is managed centrally — in VMware by vCenter — while each host still runs its own data plane locally, so forwarding survives even if the central manager is offline.

```
              ┌──────────────────────────┐
              │   Central control plane   │   (e.g. vCenter)
              └────┬───────────┬──────────┘
        config     │           │     config
        pushed     ▼           ▼     pushed
        ┌───────────────┐  ┌───────────────┐
        │ Host 1 data   │  │ Host 2 data   │   local forwarding
        │ plane (vDS)   │  │ plane (vDS)   │
        └───────────────┘  └───────────────┘
```

|Aspect|Standard switch|Distributed switch|
|---|---|---|
|Scope|One host|Many hosts, one logical switch|
|Configuration|Per host, replicated by hand|Defined once, pushed to all hosts|
|Consistency|Prone to drift|Uniform across the cluster|
|Advanced features|Basic|Central management, Network I/O Control, LACP, load-based teaming, private VLANs, port mirroring, NetFlow|
|Port state on live migration|Not preserved|Follows the VM as it moves between hosts|

## Vendor Implementations

_The same concepts under different names across the major platforms._

### VMware vSphere

The Standard Switch and Distributed Switch described above, with [[#Port Groups|port groups]] for policy, VMkernel ports for host services, and VMXNET3 as the paravirtual adapter.

### Microsoft Hyper-V

Hyper-V exposes its networking through the Hyper-V Virtual Switch, which comes in three types defined by how far their connectivity reaches.

|Switch type|Bound to a pNIC?|Who can communicate|
|---|---|---|
|External|Yes|VMs, the host, and the physical network / internet|
|Internal|No|VMs and the host (management OS) only|
|Private|No|VMs on the same host only — not the host, not the outside|

Teaming is provided by Switch Embedded Teaming (SET), and adapters are presented as synthetic (paravirtual, over the VMBus) or legacy (emulated).

### Linux and KVM

KVM builds on standard Linux networking. Each VM is given a tap device that plugs into a software bridge (the in-kernel Linux bridge), with virtio-net as the paravirtual adapter. libvirt wraps this into named networks — NAT, routed, bridged, or isolated — and macvtap offers a lower-overhead direct attachment when bridge features are not needed.

### Open vSwitch

A multilayer, programmable switch that replaces the Linux bridge when more is required: 802.1Q VLANs, VXLAN and GRE overlays, and OpenFlow control. It is the switching plane for OpenStack and many software-defined networking stacks.

## Containers versus Virtual Machines

_Both isolate workloads, but at different layers — the pairing highlights the tradeoff between isolation and density._

### Architectural Difference

A virtual machine packages a full guest operating system and runs on a hypervisor, so each VM carries its own kernel. A container isolates a process using the host kernel's own facilities (namespaces and control groups) and shares that single kernel with every other container. Containers are therefore lighter, faster to start, and denser; VMs isolate more strongly because a separate kernel per guest is a harder boundary to cross.

```
   Virtual machines               Containers
┌───────┬───────┐            ┌───────┬───────┬───────┐
│Guest  │Guest  │            │ App   │ App   │ App   │
│OS+app │OS+app │            ├───────┴───────┴───────┤
├───────┴───────┤            │  Container runtime    │
│  Hypervisor   │            ├───────────────────────┤
├───────────────┤            │   Shared host OS      │
│   Hardware    │            │      kernel           │
└───────────────┘            ├───────────────────────┤
                             │      Hardware         │
                             └───────────────────────┘
   full OS per guest            one shared kernel
```

|Aspect|Virtual machine|Container|
|---|---|---|
|Isolation boundary|Own kernel per guest|Shared host kernel|
|Overhead|Full OS per instance|Process-level, minimal|
|Startup|Seconds to minutes|Sub-second|
|Density per host|Lower|Much higher|
|Runs on|A hypervisor|A container runtime on the host OS|

### Networking Difference

A VM reaches the network through its [[#Virtual NIC|vNIC]] and the [[#Virtual Switch|vSwitch]]. A container is placed in its own network namespace and connected by a virtual Ethernet (veth) pair to a host bridge — such as the default docker0 — or to a CNI plugin that provides overlays, macvlan, or routed models. Both ultimately reach a software switch and then the physical NIC, but the container's network stack is a slice of the host kernel's stack rather than an independent one.

## Integrating with the Physical Network

_What a hypervisor host asks of the switch it plugs into._

The internal switching plane only works if the physical port is configured to match it. For VST and VGT the host-facing port is an 802.1Q trunk carrying exactly the VLANs the VMs use; a mismatch between the port-group VLAN and the VLANs allowed on the trunk black-holes the traffic. Because the [[#Virtual Switch|vSwitch]] runs no spanning tree and never bridges one uplink to another, the port behaves as an edge port — configuring it as a portfast trunk speeds up link-up, and since a well-behaved host never emits BPDUs, BPDU guard is a reasonable safeguard against a misconfiguration that would bridge the two networks. Finally, the physical switch sees one source MAC per vNIC behind a single port, so MAC-table scale and any port-security limits must account for many addresses on that interface.

```cisco
interface GigabitEthernet1/0/10
 description ESXi-host-uplink
 switchport mode trunk
 switchport trunk allowed vlan 10,20,30
 spanning-tree portfast trunk
 spanning-tree bpduguard enable
```
