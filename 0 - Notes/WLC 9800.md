The Cisco Catalyst 9800 Wireless LAN Controller is the IOS-XE controller that terminates CAPWAP tunnels from lightweight access points and centralizes their configuration, RF management and client handling. It replaced the AireOS controllers (2500/5520/8540) and runs the same software train as the Catalyst 9000 switches, so its AAA, interface and management configuration look familiar to anyone who works on those switches.

This note is a configuration reference for the controller itself: the [[#The Configuration Model|tag and profile model]] that organizes everything, the initial bring-up, how access points join, how WLANs and their security are built, and the operational commands used to run and troubleshoot it. It is deliberately self-contained — example addresses and VLANs stand in for a real site.

> [!info] The one idea to absorb first 
> The 9800 never configures an AP directly. You build reusable [[#Profiles|profiles]], group their bindings into [[#Tags|tags]], and assign one tag of each kind to each AP. Everything below is either a profile, a tag, or the glue that brings an AP online so its tags take effect.

---

# Platform Overview

_What the 9800 is, the shapes it ships in, and the one design decision — central versus local switching — that colours everything else._

The controller handles the wireless control plane for every joined AP: CAPWAP tunnel maintenance, client authentication relay, [[#RF Management|RF management]], roaming and policy. The wireless-specific configuration is layered on top of ordinary IOS-XE through the [[#The Configuration Model|tag and profile model]], which has no equivalent in AireOS.

## Form Factors

The same software image runs across every form factor; only scale and the redundancy hardware differ.

|Form factor|Where it runs|Typical use|
|---|---|---|
|C9800-80 / C9800-40|Dedicated appliance|Large campus, high AP/client count|
|C9800-L|Compact appliance (copper or fibre uplinks)|Mid-size campus|
|C9800-CL|Virtual machine (ESXi, KVM, public cloud)|Virtualized data centre, lab|
|C9800 embedded|On a Catalyst 9000 switch|Small site, switch-integrated|
|EWC (Embedded Wireless Controller)|On a Catalyst AP|Branch with no dedicated controller|

## IOS-XE Foundations

Because the controller is IOS-XE, much carries straight over from the switch world: `aaa new-model`, `radius server` blocks, named method lists, NetCONF/YANG, model-driven telemetry, and the `ip http secure-server` admin interface. Software is managed in install mode and upgraded the same way as a switch, with wireless-specific helpers for [[#Software and AP Image Management|AP images]].

## Switching Modes

_Where the client's data frames are bridged onto a VLAN — at the controller or at the AP. This single choice decides where the client VLANs must exist._

### Local Mode (Central Switching)

In local mode the AP wraps client traffic in CAPWAP and tunnels it to the controller, which bridges it onto the VLAN named by the [[#Policy Profiles|policy profile]]. The consequence is that every client VLAN must be present on the controller's uplink trunk. This is the default and is assumed throughout unless stated otherwise.

### FlexConnect (Local Switching)

In FlexConnect the AP bridges client traffic directly onto a local VLAN at the remote site; only control-plane traffic reaches the controller. It is used when APs sit behind a WAN link. The VLAN-to-SSID mapping then lives in a flex profile referenced by the [[#Site Tag|site tag]], which is marked `no local-site`. FlexConnect survives a WAN outage for already-authenticated clients (local switching continues even when the controller is unreachable).

# The Configuration Model

_The 9800 separates settings (profiles) from binding (tags). An AP carries one tag of each kind, and each tag points at the profiles that decide how that AP behaves._

![[wlc9800-tag-architecture.png]]

Build reusable profiles, group their bindings into tags, and assign one tag of each kind per AP. Change a profile once and every AP that resolves to it updates. The three tag kinds and the profiles they reference are summarised below and built with real CLI in [[#Tag Assembly and AP Assignment|Tag Assembly and AP Assignment]].

## Profiles

_Containers for the actual settings. Each profile type answers one question about the network._

| Profile         | Answers                                                                                        | Configured in                                    |
| --------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| WLAN profile    | What SSID is broadcast and how clients authenticate (L2 security)                              | [[#WLAN Profiles]]                               |
| Policy profile  | What VLAN, QoS, ACLs and switching a client gets after it joins                                | [[#Policy Profiles]]                             |
| AP join profile | How the AP itself behaves — CAPWAP timers, management, SSH, syslog                             | [[#AP Join Profile]]                             |
| Flex profile    | VLAN mapping and local-switching behavior for [[#FlexConnect (Local Switching)\| FlexConnect]] | [[#FlexConnect (Local Switching)\| FlexConnect]] |
| RF profile      | Data rates, channels and power per band                                                        | [[#RF Management]]                               |

A WLAN profile and a policy profile are always used as a pair: the WLAN says how to authenticate, the policy says what access results. The pairing is made inside the [[#Policy Tag|policy tag]].

## Tags

_The binding layer. A tag is a named bundle that points an AP at a set of profiles._

### Policy Tag

The policy tag maps one or more WLAN profiles to their corresponding policy profiles. It answers, for the APs that carry it, "which SSIDs are broadcast, and what access does each grant?" An SSID not listed in an AP's policy tag is simply not broadcast by that AP.

### Site Tag

The site tag points at an AP join profile and decides the switching mode. With the default `local-site` the APs operate in [[#Local Mode (Central Switching)|local mode]]; with `no local-site` and a flex profile they operate in [[#FlexConnect (Local Switching)|FlexConnect]]. The site tag is also the unit of AP grouping for CAPWAP load and [[#Software and AP Image Management|rolling AP upgrades]].

### RF Tag

The RF tag points at the per-band RF profiles (2.4 GHz, 5 GHz, 6 GHz). It answers "what data rates, channels and transmit power apply to the radios of these APs?" See [[#RF Management|RF Management]].

### Default Tags

Every AP that has not been explicitly mapped resolves to `default-policy-tag`, `default-site-tag` and `default-rf-tag`. A freshly joined AP therefore broadcasts whatever the default policy tag contains — which is nothing useful until configured. In production each AP is mapped to purpose-built tags as shown in [[#Mapping APs to Tags|Mapping APs to Tags]].

## How an AP Resolves Its Configuration

_The lookup an AP performs to discover what to broadcast and how to behave._

```text
AP joins controller
        │
        ▼
What tags is this AP mapped to?  (static map, or filter/location rule, else default)
        │
        ├── Policy Tag ──► WLAN Profile  +  Policy Profile   (which SSIDs, what access)
        │
        ├── Site Tag   ──► AP Join Profile  (+ Flex Profile)  (how the AP behaves, switching mode)
        │
        └── RF Tag     ──► RF Profiles per band               (rates, channels, power)
```

If any tag is missing from the mapping, the corresponding default tag is used — so a misconfigured or unmapped AP commonly shows "joined but broadcasting nothing", which is almost always a missing or empty [[#Policy Tag|policy tag]].

# Initial Bring-Up

_Everything the controller needs before any AP joins or any WLAN exists: identity, management reachability, the wireless management interface, regulatory domain, time and certificates._

## Base System

A baseline that gives SSH access and a privileged admin account, so the box is reachable for management before anything wireless is configured.

```cisco
hostname WLC-01
ip domain name example.local
!
aaa new-model
!
username admin privilege 15 secret <admin-secret>
enable secret <enable-secret>
!
ip ssh version 2
ip ssh time-out 30
!
line vty 0 4
 transport input ssh
 login authentication default
```

## VLANs

The controller needs the wireless management VLAN and, under [[#Local Mode (Central Switching)|central switching]], every client VLAN it will bridge.

```cisco
vlan 10
 name WIRELESS-MGMT
!
vlan 11
 name AP-MGMT
!
vlan 20
 name EMPLOYEE
!
vlan 30
 name GUEST
```

> [!note] The client VLANs must reach the controller 
> Under central switching the controller bridges client traffic itself, so the employee and guest VLANs must be carried on its uplink trunk (`switchport trunk allowed vlan add 20,30` on the connecting switch). FlexConnect avoids this by switching at the AP.

## Wireless Management Interface

_The single SVI the controller uses to source CAPWAP, DTLS and RADIUS. Designating it is what turns an ordinary SVI into the wireless control endpoint._

Exactly one interface is nominated as the wireless management interface. APs discover and build their CAPWAP tunnel to its address, and it is the natural source for [[#RADIUS and AAA|RADIUS]] so an external server sees a single, predictable controller IP.

```cisco
interface Vlan10
 description WIRELESS-MGMT
 ip address 10.10.10.5 255.255.255.0
 no shutdown
!
wireless management interface Vlan10
```

> [!warning] Do not renumber this casually 
> Changing the wireless management interface tears down every CAPWAP tunnel — all APs drop and rejoin. It also changes the source IP for RADIUS, so any external server's device entry must be updated to match.

## Country Code

_The regulatory domain. Radios stay administratively down until a country that matches each AP's hardware domain is set._

```cisco
ap country US
```

Multiple countries can be listed when APs span regulatory domains. The country must be compatible with each AP's hardware regulatory domain or that AP's radios will not come up.

## Time and Name Resolution

Accurate time is mandatory: certificate validation for AP join and for the admin and web-auth certificates depends on it, and any RADIUS or syslog timestamps must line up.

```cisco
clock timezone PST -8 0
clock summer-time PDT recurring
!
ntp server 10.10.0.10
ntp server 10.10.0.11 prefer
!
ip name-server 10.10.0.53 10.10.0.54
```

## Certificates

The controller ships with a self-signed certificate used for the HTTPS admin GUI, the [[#Guest Access (Web Authentication)|guest web-auth portal]], and AP join (the AP validates the controller, and the controller validates the AP via its manufacturer-installed certificate, MIC). For a guest portal presented to client browsers, install a certificate issued by a trusted CA and reference it from the web-auth parameter map so clients do not see certificate warnings.

# RADIUS and AAA

_How the controller authenticates clients and administrators against an external server. Needed by 802.1X WLANs, by guest web auth when it uses RADIUS, and optionally for admin login._

## RADIUS Servers

Define each server with its shared secret and, optionally, an automate-tester probe so the controller can mark a dead server and fail over.

```cisco
radius server RAD-1
 address ipv4 10.10.10.20 auth-port 1812 acct-port 1813
 timeout 5
 retransmit 3
 automate-tester username probe-user ignore-acct-port probe-on
 key <radius-key>
!
radius server RAD-2
 address ipv4 10.10.10.21 auth-port 1812 acct-port 1813
 timeout 5
 retransmit 3
 automate-tester username probe-user ignore-acct-port probe-on
 key <radius-key>
!
radius-server dead-criteria time 5 tries 3
radius-server deadtime 15
```

## Server Groups and Method Lists

Group the servers, then reference them through named method lists that the WLANs and policy profiles call. Sourcing RADIUS from the [[#Wireless Management Interface|wireless management interface]] keeps the controller IP consistent.

```cisco
aaa group server radius RAD-GROUP
 server name RAD-1
 server name RAD-2
 deadtime 15
 ip radius source-interface Vlan10
!
aaa authentication dot1x DOT1X-LIST group RAD-GROUP
aaa authorization network default group RAD-GROUP
aaa accounting identity ACCT-LIST start-stop group RAD-GROUP
```

| Method list         | Used by         | Purpose                        |
| ------------------- | --------------- | ------------------------------ |
| `DOT1X-LIST`        | 802.1X WLANs    | Authenticate clients via EAP   |
| `default` (network) | Policy profiles | Required for [[#AAA Override]] |
| `ACCT-LIST`         | Policy profiles | Send start/stop accounting     |

## RADIUS-Assigned Attributes

If the RADIUS server returns a VLAN or ACL with an Access-Accept, the controller applies it only when the [[#Policy Profiles|policy profile]] has `aaa-override` set. The relevant attributes are the standard tunnel attributes (`Tunnel-Type = VLAN`, `Tunnel-Medium-Type = 802`, `Tunnel-Private-Group-ID = <vlan>`). MAC and port formatting for the server's logs can be made consistent with the wired side:

```cisco
radius-server attribute 6 on-for-login-auth
radius-server attribute 31 mac format ietf upper-case
radius-server vsa send authentication
radius-server vsa send accounting
```

## Change of Authorization (CoA)

_The reverse channel: a RADIUS server reaching back into the controller to change or terminate a live session, defined by RFC 5176. Optional — only needed when something off-box drives session changes._

Where the configuration above lets the controller initiate authentication, CoA lets a server initiate a change afterwards: disconnect a session, push new attributes, or change a client's bandwidth. It is the mechanism behind an external captive portal (the portal authenticates the user, then the policy server re-authorizes the session) and behind administrative client disconnects.

```cisco
aaa server radius dynamic-author
 client 10.10.10.20 server-key <coa-key>
 client 10.10.10.21 server-key <coa-key>
 auth-type any
```

For CoA to land on a session, the session must be accounting-enabled and, when a server is driving a portal redirect, the [[#Policy Profiles|policy profile]] enables `nac` so the controller accepts the re-authorization. If no server initiates session changes, this block can be omitted.

## Administrative Authentication

Admin access to the GUI/CLI can be backed by the same servers, with local fallback so a server outage never locks you out.

```cisco
aaa authentication login default group RAD-GROUP local
aaa authorization exec default group RAD-GROUP local if-authenticated
ip http authentication aaa login-authentication default
```

TACACS+ can back administration instead of RADIUS (`aaa group server tacacs+`, `tacacs server <name>`) when device admin is centralised on a TACACS+ server, while client authentication stays on RADIUS.

# AP Join Process

_How an access point finds the controller, builds a secure tunnel, is admitted, and is brought into service._

## CAPWAP Discovery

The AP must learn the [[#Wireless Management Interface|wireless management address]] before it can build a tunnel. Discovery methods, tried in order:

| Method          | Mechanism                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------- |
| Static / primed | A previously joined AP remembers the controller, or is primed with `capwap ap primary-base` |
| DHCP option 43  | The AP's DHCP scope returns the controller IP in option 43                                  |
| DNS             | The AP resolves `CISCO-CAPWAP-CONTROLLER.<domain>`                                          |
| Broadcast       | Layer-2 broadcast discovery on the local subnet                                             |
| Mobility        | A controller in the same [[#Mobility]]                                                      |

Option 43 on the AP management scope (VLAN 11 here) is the usual choice when APs are in a dedicated subnet routed away from the controller.

## DTLS and AP Authorization

The CAPWAP control channel is secured with DTLS, and mutual certificate validation happens automatically — the AP presents its manufacturer-installed certificate (MIC) and the controller presents its own. The controller can additionally gate which APs may join.

```text
AP sends Join Request (DTLS, MIC presented)
        │
        ▼
Controller authorization
   ├── allow all  (trusted L2)                  ──► AP admitted
   └── authorize-mac (against a list or AAA)    ──► only known APs admitted
        │
        ▼
Config download: country, AP join profile (via Site Tag), tags resolved, image checked
        │
        ▼
Radios come up with the WLANs from the Policy Tag
```

## AP Modes

An AP's mode is set in the [[#AP Join Profile|AP join profile]] / via the site tag's switching choice, and a few special modes are set per-AP.

| Mode          | Behaviour                                                      |
| ------------- | -------------------------------------------------------------- |
| Local         | Normal client serving with [[#Local Mode (Central Switching)]] |
| FlexConnect   | Client serving with [[#FlexConnect (Local Switching)]]         |
| Monitor       | No client serving; dedicated scanning for RRM/aWIPS            |
| Sniffer       | Captures frames and forwards them to a packet analyser         |
| Bridge / Mesh | Wireless backhaul between APs                                  |

## AP Join Profile

_The profile that configures the AP itself — not its WLANs, but how the AP is managed and behaves. It is bound to APs through the [[#Site Tag|site tag]]._

Where WLAN and policy profiles shape the client experience, the AP join profile shapes the AP: its local admin credentials, whether SSH to the AP is allowed, where it sends syslog, its CAPWAP timers, and whether the CAPWAP data path is DTLS-encrypted.

```cisco
ap profile AP-JOIN-CAMPUS
 description Campus AP Join Profile
 mgmtuser username apadmin password 0 <ap-pass> secret 0 <ap-secret>
 ssh
 syslog host 10.10.0.20
 link-encryption
 ! also configured here: AP NTP source, CAPWAP retransmit timers,
 ! hyperlocation, and per-profile rogue/aWIPS behaviour
```

`link-encryption` turns on DTLS for the CAPWAP data path (control is always encrypted); `mgmtuser` sets the credentials used to reach the AP console/SSH. The profile is then referenced by the [[#Building the Site Tag|site tag]].

## Priming and Tag Assignment

On first join the AP downloads the AP join profile referenced by its [[#Site Tag|site tag]], takes the [[#Country Code|country]], checks its [[#Software and AP Image Management|software image]], and resolves its [[#Mapping APs to Tags|tag assignment]]. Only then do its radios come up and begin broadcasting the SSIDs in its [[#Policy Tag|policy tag]]. The common first-join symptom — AP joins but no SSID — traces back to the default policy tag being empty.

# WLAN Profiles

_The SSID and its Layer-2 security. The WLAN profile decides how a client proves who it is; the resulting access is decided later by the paired [[#Policy Profiles|policy profile]]._

## Anatomy of a WLAN

A WLAN profile has a profile name, an SSID (the broadcast name) and a numeric ID. It is created shut and is only broadcast once it is referenced by a [[#Policy Tag|policy tag]] carried by an AP.

```cisco
wlan <profile-name> <id> <ssid>
 ...security and options...
 no shutdown
```

## WPA2/WPA3-Enterprise (802.1X)

_The corporate SSID. Clients run an EAP supplicant and are authenticated by a RADIUS server; the controller is the authenticator relaying RADIUS._

```cisco
wlan Corp 1 Corp-SSID
 security wpa wpa2
 security wpa wpa2 ciphers aes
 security wpa akm dot1x
 security dot1x authentication-list DOT1X-LIST
 no shutdown
```

WPA3-Enterprise swaps the AKM and makes Protected Management Frames mandatory:

```cisco
 security wpa wpa3
 security wpa wpa3 ciphers aes
 security wpa akm dot1x-sha256
 security pmf mandatory
```

The authentication uses [[#Server Groups and Method Lists|DOT1X-LIST]]; a VLAN the server returns is applied through [[#Policy Profiles|AAA override]] in the policy profile.

> [!note] WPA3-Enterprise 192-bit The 192-bit suite (`security wpa akm suite-b-1x` with GCMP-256) requires EAP-TLS end to end and matching client cipher support. Use standard WPA3-Enterprise unless a compliance mandate requires it.

## WPA2/WPA3-Personal (PSK / SAE)

_A pre-shared-key SSID for devices that cannot run a supplicant. No RADIUS at association time._

```cisco
wlan IoT 2 IoT-SSID
 security wpa psk set-key ascii 0 <passphrase>
 security wpa akm psk
 security wpa wpa2
 security wpa wpa2 ciphers aes
 no shutdown
```

WPA3-Personal replaces PSK with SAE and requires PMF:

```cisco
 security wpa akm sae
 security wpa wpa3
 security wpa wpa3 ciphers aes
 security pmf mandatory
```

A transition WLAN can advertise WPA2-PSK and WPA3-SAE together for mixed client estates, at the cost of WPA3's downgrade protection.

## Identity PSK (iPSK)

_One PSK SSID, but a different key per device or group, handed out by a RADIUS server keyed on MAC. Lets a single IoT SSID segment many device types without a separate SSID for each._

```cisco
wlan IoT-iPSK 5 IoT-iPSK
 mac-filtering MAC-AUTHZ
 security wpa psk set-key ascii 0 <fallback-psk>
 security wpa akm psk
 security wpa wpa2
 security wpa wpa2 ciphers aes
 no shutdown
```

The `mac-filtering MAC-AUTHZ` clause MAC-authenticates each client (`aaa authorization network MAC-AUTHZ group RAD-GROUP`); the server returns that device's individual PSK in a vendor attribute. Different devices on the same SSID therefore use different keys, and the policy can place each group on its own VLAN through [[#AAA Override|AAA override]].

## Enhanced Open (OWE)

_Opportunistic Wireless Encryption: an open network that is nonetheless encrypted per client. A good fit for a guest SSID where a captive portal is not wanted._

```cisco
wlan Open 4 Open-SSID
 security wpa wpa3
 security wpa wpa3 ciphers aes
 security wpa akm owe
 security pmf mandatory
 no shutdown
```

> [!note] 6 GHz is WPA3/OWE only The 6 GHz band forbids open and WPA2: a WLAN that broadcasts on 6 GHz must use WPA3-Enterprise, WPA3-SAE, or OWE, each with `pmf mandatory`. 6 GHz also changes discovery — APs advertise their 6 GHz BSSs out-of-band through the Reduced Neighbor Report (RNR) carried in 2.4/5 GHz beacons, with broadcast/unicast probe responses and optional FILS. A WPA2/WPA3 transition SSID therefore only lands on 2.4/5 GHz; its 6 GHz radio carries the WPA3 or OWE variant.

## Guest Access (Web Authentication)

_An open SSID gated by a captive portal. In Local Web Authentication the controller hosts the portal itself; in Central Web Authentication an external policy server hosts it._

Local Web Authentication (LWA) needs a web-auth parameter map and a WLAN that runs web auth over an open L2:

```cisco
parameter-map type webauth WEBAUTH-GUEST
 type webauth
 banner text ^Welcome to Guest WiFi^
!
wlan Guest 3 Guest-SSID
 no security wpa
 no security wpa akm dot1x
 no security wpa wpa2 ciphers aes
 security web-auth
 security web-auth authentication-list DOT1X-LIST
 security web-auth parameter-map WEBAUTH-GUEST
 no shutdown
```

The parameter-map `type` selects the experience: `webauth` (username/password against local users or RADIUS), `consent` (accept terms only), or `authbypass`. The global parameter map supplies the virtual IP used to terminate the intercepted session:

```cisco
parameter-map type webauth global
 virtual-ip ipv4 192.0.2.1
 trustpoint <portal-trustpoint>
 intercept-https-enable
```

> [!note] Central Web Authentication When an external policy server owns the portal and returns a redirect URL plus a named redirect ACL, the WLAN uses MAC filtering instead of `security web-auth`, and the [[#Policy Profiles|policy profile]] enables `aaa-override` and `nac`. That model is out of scope here; LWA above keeps the portal on the controller.

## Common WLAN Options

Options that apply regardless of security type, set on the WLAN profile.

|Option|Effect|
|---|---|
|`broadcast-ssid` / `no broadcast-ssid`|Advertise or hide the SSID in beacons|
|`radio policy dot11 5ghz`|Restrict the SSID to a band (e.g. 5 GHz only)|
|`band-select`|Steer dual-band clients toward 5 GHz|
|`security ft` / `security ft adaptive`|Enable 802.11r fast transition (see [[#Fast Roaming|
|`assisted-roaming` (802.11k/v)|Provide neighbour lists and BSS transition hints|
|`client vlan ...`|Per-WLAN VLAN override (otherwise from the policy profile)|

# Policy Profiles

_What a client receives after it joins: the VLAN, switching mode, QoS, ACLs and session timers. The policy profile is paired with a [[#WLAN Profiles|WLAN profile]] inside the [[#Policy Tag|policy tag]]._

## VLAN and Switching

A policy profile names a default VLAN. Under [[#Local Mode (Central Switching)|central switching]] this VLAN must exist on the controller's uplink trunk. A policy profile is created shut; `no shutdown` is required before it carries traffic.

```cisco
wireless profile policy PP-Corp
 description Corporate clients - central switching
 vlan 20
 no shutdown
```

For a [[#FlexConnect (Local Switching)|FlexConnect]] deployment the same profile carries `no central switching` and the VLAN is resolved from the flex profile at the AP.

## AAA Override

If a RADIUS server returns a VLAN or ACL, the controller honours it only when `aaa-override` is enabled; otherwise the static VLAN above applies.

```cisco
wireless profile policy PP-Corp
 aaa-override
 vlan 20
 no shutdown
```

## QoS and Application Visibility

QoS is applied per policy profile, either as one of the built-in metal profiles or a custom policy, and Application Visibility and Control (AVC) can be attached for per-application reporting and control.

```cisco
wireless profile policy PP-Corp
 service-policy input  platinum-up
 service-policy output platinum
 ! ip flow monitor / AVC profile attached here for application visibility
 no shutdown
```

For voice, Call Admission Control (CAC) reserves radio airtime for SIP/voice so calls are not admitted beyond capacity, and Fastlane optimises QoS marking end-to-end for Apple clients.

## Session Timers and ACLs

Session and idle timeouts bound how long a client stays authorized, and ACLs can be attached as a floor.

```cisco
wireless profile policy PP-Corp
 session-timeout 86400
 idle-timeout 3600
 no shutdown
```

## DHCP and Client Handling

_Address learning and lateral-traffic controls, also set on the policy profile._

```cisco
wireless profile policy PP-Guest
 ipv4 dhcp required
 no shutdown
```

`ipv4 dhcp required` forces a client to obtain an address by DHCP before traffic is allowed, so the controller learns the client IP that web auth and IP-based ACLs depend on. Peer-to-peer (client-to-client) blocking and client exclusion — auto-quarantining clients that repeatedly fail association or authentication — are also configured here; enabling peer-to-peer blocking on guest and IoT WLANs stops lateral traffic between clients on the same SSID.

# Tag Assembly and AP Assignment

_Building the three tags from the profiles above and binding them to APs. This is the step that actually puts SSIDs on the air._

## Building the Policy Tag

The policy tag maps each WLAN profile to its policy profile. Listing a WLAN here is what causes carrying APs to broadcast it.

```cisco
wireless tag policy PT-Campus
 wlan Corp  policy PP-Corp
 wlan Guest policy PP-Guest
```

## Building the Site Tag

The site tag references the [[#AP Join Profile|AP join profile]] and sets the switching mode. The default `local-site` keeps APs in [[#Local Mode (Central Switching)|local mode]].

```cisco
wireless tag site ST-Campus
 ap-profile AP-JOIN-CAMPUS
 ! AP-JOIN-CAMPUS is defined under AP Join Profile; local-site (default) = central switching
```

A FlexConnect site instead carries `flex-profile FP-Branch` and `no local-site`.

## Building the RF Tag

The RF tag references per-band [[#RF Profiles and Tags|RF profiles]].

```cisco
wireless tag rf RT-Campus
 24ghz-rf-policy RF-24-Campus
 5ghz-rf-policy  RF-5-Campus
 6ghz-rf-policy  RF-6-Campus
```

## Mapping APs to Tags

Each AP is bound to one tag of each kind. The static method maps by AP Ethernet MAC; persistency keeps the mapping across reloads.

```cisco
ap F4BD.9E11.2233
 policy-tag PT-Campus
 site-tag   ST-Campus
 rf-tag     RT-Campus
!
ap tag persistency enable
```

At scale, filter or location rules assign tags automatically by AP-name pattern or join location, avoiding per-AP CLI. An AP that resolves to no explicit mapping falls back to the [[#Default Tags|default tags]].

# Mobility

_How controllers cooperate so clients roam seamlessly and guest traffic can be tunneled to a DMZ controller._

## Mobility Groups

Controllers that share clients form a mobility group; members exchange a CAPWAP-based mobility tunnel so a client roaming from an AP on one controller to an AP on another keeps its session.

```cisco
wireless mobility group name CAMPUS-MOBILITY
wireless mobility group member ipv4 10.20.10.5 public-ip 10.20.10.5 group CAMPUS-MOBILITY
```

A client roaming within a mobility group does an intra- or inter-controller roam without re-authenticating from scratch, especially when [[#Fast Roaming|fast roaming]] is enabled.

## Guest Anchor

For guest isolation, foreign controllers tunnel guest traffic to an anchor controller in the DMZ; clients terminate their data path there rather than on the internal network. The guest [[#Policy Profiles|policy profile]] names the anchor.

```cisco
wireless profile policy PP-Guest
 mobility anchor 192.0.2.50
 no shutdown
```

On the anchor controller the same profile points `mobility anchor` at itself, completing the export-foreign / export-anchor relationship.

## Fast Roaming

For latency-sensitive clients (voice, real-time apps), fast-roaming methods cut the re-authentication delay on roam.

|Method|Mechanism|
|---|---|
|802.11r (FT)|Pre-computes keys so the roam skips the full EAP exchange (`security ft` on the WLAN)|
|Adaptive 802.11r|Negotiates FT only with capable clients, avoiding breakage on legacy ones|
|OKC|Opportunistic Key Caching reuses the PMK across APs on the same controller|
|802.11k / v|Neighbour lists and BSS transition hints help the client pick the next AP|

# Multicast and mDNS

_How the controller delivers multicast to wireless clients, and how it bridges link-local service discovery (AirPlay, AirPrint, Chromecast) across VLANs._

## Multicast Delivery

The controller replicates multicast to APs either by unicast or by multicast. Multicast-multicast sends one CAPWAP multicast stream that all APs in a group receive — efficient, but it needs multicast routing on the wired network. Multicast-unicast needs no wired multicast but the controller sends a separate copy to each AP, which scales poorly with AP count.

```cisco
wireless multicast
ap multicast mode multicast 239.10.10.1
! omit 'ap multicast mode multicast' to fall back to multicast-unicast
```

IGMP (and MLD for IPv6) snooping should be enabled so a stream is only delivered to APs with clients that have joined it, rather than flooded.

## mDNS Gateway

By default mDNS/Bonjour is link-local, so an AirPrint printer on one VLAN is invisible to a client on another. The controller's mDNS gateway learns advertised services and re-advertises them across VLANs and WLANs according to an mDNS service policy applied in the [[#Policy Profiles|policy profile]].

```cisco
mdns-gateway
!
wireless profile policy PP-Corp
 mdns-sd service-policy <mdns-policy>
 no shutdown
```

The service policy controls which service types (AirPlay, AirPrint, screen mirroring) are bridged and between which VLANs, so discovery is shared deliberately rather than wholesale.

# RF Management

_Automatic radio resource management and the per-band profiles that constrain it. RRM does most of the work; profiles set the boundaries._

## RRM

Radio Resource Management continuously tunes the radios per band and per RF group.

|Function|What it does|
|---|---|
|DCA (Dynamic Channel Assignment)|Picks channels to minimise co-channel interference|
|TPC (Transmit Power Control)|Adjusts AP power so cells size correctly without overlap|
|Coverage Hole Detection/Mitigation|Detects weak coverage from client RSSI and raises power|
|RF grouping|Elects an RF group leader that runs DCA/TPC across the group|

Flexible Radio Assignment (FRA) additionally decides, for dual-band XOR radios, whether a radio serves 2.4 GHz, 5 GHz, or acts as a monitor — useful where 2.4 GHz is already dense.

## RF Profiles and Tags

An RF profile sets data rates, allowed channels and power limits for one band; an [[#RF Tag|RF tag]] bundles the three bands and is assigned to APs via [[#Mapping APs to Tags|tag mapping]]. Typical adjustments are disabling low legacy data rates (to discourage sticky clients and cut airtime overhead), constraining channel width, and tuning the receiver start-of-packet threshold (RX-SOP) for high-density rooms.

```cisco
ap dot11 5ghz rf-profile RF-5-Campus
 description 5 GHz - campus
 channel width 40
 ! disable low mandatory/supported rates and tune RX-SOP per density
```

# High Availability

_Keeping wireless up if a controller fails. Two models, chosen at deployment time._

## SSO Redundancy

A 1+1 Stateful Switchover pair presents as a single controller. Client and AP state are synchronized over a dedicated Redundancy Port (RP), with a Redundancy Management Interface (RMI) for gateway-reachability health checks. Failover is sub-second and APs do not rejoin (AP SSO). Both units must run the same model and software version.

```cisco
! Redundancy Management Interface and chassis priority (active = higher priority)
chassis 1 priority 2
chassis 2 priority 1
redun-management interface Vlan10 chassis 1 address 10.10.10.6 chassis 2 address 10.10.10.7
```

The RP is a back-to-back physical link between the two chassis (a dedicated vNIC on the C9800-CL) over which state is synchronised; its exact setup is platform-specific. Verify the pair with:

```cisco
show redundancy
show chassis
show wireless stats redundancy summary
```

## N+1

Without an SSO pair, APs can be primed with a secondary (and tertiary) controller. On primary failure APs rejoin the backup — a longer, stateless recovery, but no dedicated redundancy hardware is needed. An HA-SKU controller can serve as the shared N+1 backup for several primaries.

# Software and AP Image Management

_Upgrading the controller and the APs it serves with the least disruption to clients._

## Controller Software

The controller runs in install mode; an upgrade adds, activates and commits a new image package.

```cisco
install add file bootflash:C9800-universalk9.<ver>.SPA.bin activate commit
```

## AP Images

APs run an image matched to the controller's. Rather than every AP downloading the new image at reload time, predownload pushes it ahead of the upgrade so the reload window is short.

```cisco
ap image predownload
show ap image
```

A rolling AP upgrade reloads APs in staggered batches (by percentage or by [[#Site Tag|site tag]]) so neighbouring APs keep coverage up while a batch reboots. Efficient AP image upgrade lets a few APs in a site download from the controller and seed the rest locally, reducing WAN load on [[#FlexConnect (Local Switching)|FlexConnect]] sites.

# Management and Monitoring

_Getting logs, traps and operational state off the controller — by classic syslog/SNMP, or by model-driven telemetry to a controller like Catalyst Center._

## Logging

Send syslog to a collector, sourced from the [[#Wireless Management Interface|management interface]] so the source IP is predictable, with timestamps that line up with other devices.

```cisco
logging host 10.10.0.20
logging source-interface Vlan10
logging trap informational
service timestamps log datetime msec localtime
```

## SNMP

SNMPv3 is preferred for authenticated, encrypted polling and traps; v2c communities are simpler but send credentials in clear text.

```cisco
snmp-server group NETMON v3 priv read SNMP-VIEW
snmp-server user monitor NETMON v3 auth sha <auth-pass> priv aes 128 <priv-pass>
snmp-server host 10.10.0.20 version 3 priv monitor
snmp-server enable traps wireless
```

## NetCONF and Telemetry

The controller exposes its full configuration and operational state through NETCONF/YANG, and can stream operational data to a collector with model-driven telemetry rather than being polled.

```cisco
netconf-yang
```

In practice the 9800 is commonly managed by Cisco Catalyst Center (formerly DNA Center), which uses NETCONF plus streaming telemetry to push [[#Tags|tag and profile]] configuration and to assure the wireless network. Standalone, syslog and SNMP traps to a network management station cover monitoring.

# Verification and Troubleshooting

_The commands that confirm APs joined, tags resolved, clients connected and radios healthy — and the trace tools when a client will not connect._

## Status Commands

```cisco
show wireless summary
show ap summary
show ap tag summary
show wireless tag summary
show wlan summary
show wireless profile policy summary
show wireless client summary
show wireless client mac-address <mac> detail
show ap dot11 5ghz summary
```

`show ap tag summary` is the fastest way to catch the "joined but silent AP" problem — it shows whether the AP resolved to the intended [[#Building the Policy Tag|policy tag]] or fell back to [[#Default Tags|default]].

## RADIUS and AAA Checks

```cisco
show aaa servers
test aaa group RAD-GROUP probe-user <password> new-code
show wireless client mac-address <mac> detail | include VLAN|ACL|State
```

`show aaa servers` reports each server as alive or dead with the automate-tester result; a server stuck dead points at the shared key, reachability from the [[#Wireless Management Interface|management VLAN]], or the [[#RADIUS Servers|probe user]] not existing on the server.

## RadioActive Tracing

_The 9800's per-client trace. It follows one MAC across association, authentication and policy — the first tool to reach for on a connection failure._

```cisco
debug wireless mac <client-mac> internal
! reproduce the client connection attempt, then stop and collect:
no debug wireless mac <client-mac> internal
show logging profile wireless start last 30 minutes filter mac <client-mac> to-file bootflash:ra-trace.txt
```

The trace makes the authentication exchange explicit: the EAP or PSK result, the attributes any RADIUS server returned, whether [[#AAA Override|AAA override]] applied a VLAN, and where in association/DHCP a failing client stalls.

## Packet Capture

For deeper analysis, a controller-side capture or an AP placed in [[#AP Modes|sniffer mode]] captures the CAPWAP or over-the-air frames.

```cisco
monitor capture MYCAP interface <uplink> match any
monitor capture MYCAP start
! ...reproduce...
monitor capture MYCAP stop
monitor capture MYCAP export bootflash:mycap.pcap
```

# Hardening

_Reducing the controller's and APs' attack surface. Most items mirror a switch baseline; the wireless-specific ones concern AP join and rogue management._

## Management Plane

```cisco
no ip http server
ip http secure-server
ip http authentication aaa login-authentication default
ip http secure-active-session-modules none
!
line vty 0 4
 transport input ssh
```

Disable plain HTTP and Telnet, keep HTTPS/SSH with [[#Administrative Authentication|RADIUS-backed login]] and local fallback, and install a CA-issued certificate for the admin GUI and the [[#Guest Access (Web Authentication)|guest portal]].

## AP Join Security

Restrict which APs may join rather than allowing any AP on the management VLAN, so a rogue or misconfigured AP cannot join and pull down the [[#AP Join Profile|AP join profile]].

```cisco
ap auth-list authorize-mac
ap auth-list method-list <list>
```

## Rogue and aWIPS

The controller's rogue detection classifies unknown APs and clients, and the optional Advanced Wireless Intrusion Prevention System (aWIPS) adds signature-based detection of wireless attacks. Rogue rules and containment are managed centrally and reported to the monitoring platform.
